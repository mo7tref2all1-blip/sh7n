# 2. وثيقة متطلبات النظام التفصيلية (SRS)

## 2.1 نظرة عامة تقنية

| المكوّن | التقنية | ملاحظات التوافق مع cPanel |
|---|---|---|
| Backend Framework | Laravel 12 (PHP 8.3+) | متوافق مع أي استضافة cPanel حديثة تدعم Composer/SSH |
| قاعدة البيانات | MySQL 8.0 | قياسي في cPanel |
| الكاش | Redis (VPS) أو **Database/File Cache Driver** (Shared Hosting) | Laravel يدعم التبديل بمتغير بيئة واحد `CACHE_STORE` |
| الطوابير (Queue) | Redis+Horizon (VPS) أو **`database` queue driver + Cron** (Shared Hosting) | `QUEUE_CONNECTION=database`, Cron ينفذ `queue:work --stop-when-empty` كل دقيقة |
| الجدولة (Scheduler) | Laravel Task Scheduling عبر Cron entry واحد (`* * * * * php artisan schedule:run`) | مدعوم قياسيًا في cPanel > Cron Jobs |
| الواجهة الأمامية | Blade + Bootstrap 5 + Alpine.js (خفيف) أو Vue 3 (لأجزاء تفاعلية كالخرائط/الجداول الحية) | تُبنى الأصول عبر Vite محليًا وتُرفع كملفات static — لا حاجة لـ Node runtime على السيرفر |
| الخرائط | OpenStreetMap + Leaflet.js | مجاني، لا يتطلب مفاتيح API مدفوعة |
| التخزين | Local Disk (`storage/app/public`) بدايةً، مع دعم S3-compatible لاحقًا | روابط عبر symlink `storage:link` |
| البحث | MySQL Full-Text / Laravel Scout (Database driver) بدايةً | يمكن الترقية لـ Meilisearch عند VPS |
| الإشعارات | WhatsApp Cloud API, Firebase Cloud Messaging (Push), SMS Gateway محلي (مثل Vodafone/etisalat/oursms/Msegat), SMTP للبريد | كلها HTTP APIs خارجية — لا تتطلب موارد سيرفر إضافية |
| SSL | Let's Encrypt (AutoSSL مدمج في cPanel) | مجاني وتلقائي |

## 2.2 المتطلبات الوظيفية (Functional Requirements)

يتم ترقيم كل متطلب بمعرّف فريد (FR-xxx) للربط مع خطط الاختبار لاحقًا.

### 2.2.1 إدارة المستخدمين والصلاحيات
- **FR-001**: النظام يدعم تسجيل دخول موحد بأدوار متعددة (Multi-Role) عبر Guard منفصل لكل بورتال (Admin, Merchant, Agent, Driver).
- **FR-002**: كل مستخدم يمتلك دورًا أساسيًا واحدًا أو أكثر (Role) مبنيًا على RBAC مع صلاحيات دقيقة (Permission) قابلة للتخصيص لكل دور أو حتى تخصيص استثنائي لكل مستخدم.
- **FR-003**: دعم المصادقة الثنائية (2FA) عبر OTP (WhatsApp/SMS) للأدوار الحساسة (Owner, Accountant).
- **FR-004**: قفل الحساب تلقائيًا بعد عدد محاولات دخول فاشلة، مع سجل IP/جهاز.

### 2.2.2 إدارة الفروع
- **FR-010**: إنشاء/تعديل/تعطيل فرع مع تحديد المحافظة، المناطق التابعة له، والموظفين.
- **FR-011**: تسجيل عملية "نقل شحنات بين فرعين" (Branch Transfer) كسجل مستقل بحالة (Pending/In Transit/Received) ورقم مرجعي.
- **FR-012**: عرض "مخزون الفرع اللحظي" — كل الشحنات الموجودة فعليًا داخل الفرع الآن.
- **FR-013**: تسجيل عُهدة الفرع (شحنات + نقدية) وربطها بموظف مسؤول.
- **FR-014**: تقرير أداء الفرع (عدد الشحنات، نسبة التسليم، متوسط زمن المعالجة).

### 2.2.3 إدارة التجار
- **FR-020**: تسجيل تاجر جديد (يدويًا من الأدمن أو Self-Registration مع اعتماد لاحق).
- **FR-021**: كل تاجر يملك أكثر من مستخدم فرعي (Merchant Employee) بصلاحيات محدودة (مثال: موظف إدخال شحنات فقط بدون رؤية مالية).
- **FR-022**: Dashboard تاجر تعرض: إجمالي الشحنات، تم التسليم، المرتجعات، نسبة النجاح، إجمالي التحصيلات، الرصيد الحالي، المستحقات، سجل التسويات.
- **FR-023**: إنشاء شحنة يدويًا (نموذج واحد).
- **FR-024**: رفع شحنات عبر Excel/CSV مع قالب جاهز للتحميل، ومعالجة غير متزامنة (Queue) تدعم آلاف الصفوف مع تقرير أخطاء تفصيلي بعد الانتهاء.
- **FR-025**: إنشاء شحنات جماعية عبر API (Bulk Create Endpoint).
- **FR-026**: تتبع الشحنة (Timeline كامل بكل الحالات والأوقات والمواقع).
- **FR-027**: تحميل تقارير (PDF/Excel) قابلة للتصفية بالتاريخ/الحالة/المنطقة.
- **FR-028**: عرض سياسة الإرجاع والتسعير الخاصة بالتاجر (للقراءة فقط، التعديل من الأدمن).

### 2.2.4 نظام الشحنات (دورة الحياة)
- **FR-030**: كل شحنة تمر بحالات محددة ضمن Workflow قابل للتخصيص (تفصيل كامل في [05-Workflows.md](./05-Workflows.md)).
- **FR-031**: كل تغيير حالة يُسجَّل في `shipment_status_history` مع (المستخدم، الوقت، الموقع الجغرافي إن وجد، السبب/الملاحظة).
- **FR-032**: دعم "محاولات تسليم متعددة" (Delivery Attempts) لكل شحنة مع سبب لكل محاولة فاشلة (لا يرد، مؤجل، عنوان خاطئ...).
- **FR-033**: دعم الشحنات المُجدولة (Scheduled Delivery Date) وإعادة الجدولة من قِبل العميل عبر رابط تتبع عام.
- **FR-034**: صفحة تتبع عامة (Public Tracking Page) بدون تسجيل دخول عبر رقم الشحنة/QR.

### 2.2.5 نظام العهدة (Custody)
- **FR-040**: كل شحنة لها "حامل عهدة حالي" (Current Custodian) من نوع: فرع / مندوب / وكيل / سيارة / مخزن.
- **FR-041**: أي نقل عهدة يتطلب تأكيد الطرفين (تسليم/استلام) عبر مسح QR/Barcode، ويُنشئ سجلًا في `shipment_custody_log`.
- **FR-042**: تقرير "عُهدة حالية" لكل مندوب/وكيل/فرع في أي لحظة (كل الشحنات التي بحوزته الآن).

### 2.2.6 QR & Barcode
- **FR-050**: توليد Barcode (Code128) و QR Code فريدين لكل شحنة عند الإنشاء، يُطبعان على بوليصة الشحن (AWB — Airway Bill).
- **FR-051**: دعم المسح الضوئي عبر كاميرا الجهاز (PWA/Mobile) لكل عمليات الاستلام/التسليم/الجرد/المرتجعات دون الحاجة لجهاز Scanner مخصص.
- **FR-052**: دعم "المسح الجماعي" (Batch Scan) عند استلام دفعة شحنات في الفرع دفعة واحدة.

### 2.2.7 واجهة/تطبيق المندوب
- **FR-060**: Dashboard يومية: عدد الشحنات المخصصة، المسلمة، المرتجعة، المتبقية، إجمالي التحصيل النقدي بحوزته.
- **FR-061**: استلام شحنة (Scan + تأكيد).
- **FR-062**: تسليم شحنة: تحديث الحالة + POD (حسب إعدادات التاجر) + تسجيل GPS + Timestamp.
- **FR-063**: إرجاع شحنة مع سبب إلزامي من قائمة أسباب محددة مسبقًا (وسبب حر اختياري).
- **FR-064**: رفع صورة إثبات تسليم و/أو Screenshot لمكالمة مع العميل.
- **FR-065**: العمل شبه Offline (PWA Service Worker): تخزين مؤقت محلي لعمليات المسح والتسليم عند انقطاع الإنترنت، ومزامنة تلقائية عند عودة الاتصال.

### 2.2.8 إثبات التسليم (POD)
- **FR-070**: حقول POD الإلزامية دائمًا على مستوى النظام: GPS + Timestamp + الحالة النهائية للشحنة.
- **FR-071**: حقول POD قابلة للتخصيص **لكل تاجر على حدة** (Merchant POD Policy): صورة التسليم (إلزامي/اختياري/معطّل)، توقيع العميل (إلزامي/اختياري/معطّل)، ملاحظات.
- **FR-072**: عند تفعيل شرط إلزامي، لا يمكن للمندوب إتمام حالة "تم التسليم" دون استيفائه (Validation على مستوى الـ API أيضًا وليس الواجهة فقط).

### 2.2.9 الدفع والتحصيل
- **FR-080**: كل شحنة تحمل: طريقة دفع (COD / Prepaid / Visa on Delivery / Bank Transfer / Wallet Payment)، هل التحصيل مطلوب (Yes/No)، المبلغ المطلوب تحصيله، المبلغ المُحصَّل فعليًا.
- **FR-081**: دعم التحصيل الجزئي (Partial Collection) مع تسجيل الفرق كـ "مديونية على العميل" أو "خصم من التاجر" حسب السياسة.
- **FR-082**: دعم تعديل المبلغ عند التسليم (فرق سعر الشحن المدفوع من العميل) مع صلاحية خاصة وسجل تدقيق.

### 2.2.10 فصل الحالة التشغيلية عن المالية
- **FR-090**: حقلان مستقلان تمامًا على مستوى قاعدة البيانات: `shipment_status` (تشغيلي) و `financial_status` (مالي: Uncollected / Collected / Received By Branch / Received By Company / Settled To Merchant).
- **FR-091**: لوحة تحكم مخصصة (Financial Reconciliation Board) تعرض تقاطع الحالتين (مثال: كل الشحنات "Delivered" لكنها "Uncollected" = تنبيه فوري).

### 2.2.11 العهدة النقدية (Cash In Hand)
- **FR-100**: لكل مندوب/وكيل/فرع رصيد نقدي محسوب لحظيًا = (مجموع التحصيلات) − (مجموع التوريد للجهة الأعلى).
- **FR-101**: عملية "توريد نقدية" (Cash Handover) من مندوب لفرع، أو من فرع للشركة، أو من وكيل للشركة — بسجل موثق (رقم إيصال، المبلغ، المستلم، الوقت).
- **FR-102**: تنبيه تلقائي عند تجاوز عهدة مندوب حدًا أقصى محددًا (Cash Limit Alert).
- **FR-103**: تقرير مطابقة يومي (Daily Cash Reconciliation Report) لكل مستوى (مندوب ← فرع ← شركة).

### 2.2.12 المحفظة الإلكترونية (Wallet)
- **FR-110**: محفظة تاجر بسجل حركات كامل (Ledger): رصيد سابق، تحصيلات، خصومات (شحن/مرتجعات)، تسويات، مع رصيد لحظي محسوب من مجموع الحركات (Append-only Ledger، لا تعديل مباشر للرصيد).
- **FR-111**: محفظة وكيل مماثلة: عمولات، تحصيلات، خصومات، مستحقات.
- **FR-112**: كل حركة محفظة مرتبطة بمصدرها (رقم شحنة / رقم تسوية / تعديل يدوي بصلاحية خاصة + سبب إلزامي).

### 2.2.13 نظام التسعير
- **FR-120**: قواعد تسعير أساسية حسب: المحافظة، المنطقة، الوزن (شرائح وزن)، نوع الخدمة (عادي/إكسبريس/نفس اليوم).
- **FR-121**: تسعير مخصص لكل تاجر (Override) يتفوق على التسعير العام عند وجوده.
- **FR-122**: سياسة مرتجع مخصصة لكل تاجر: مرتجع مجاني / نسبة خصم على تكلفة المرتجع / نسبة تحمل من التاجر.
- **FR-123**: باقات تسعير جاهزة (Silver/Gold/Platinum) قابلة للتخصيص والتعيين للتاجر، بحزم منفصلة لأسعار الشحن وأسعار المرتجعات.

### 2.2.14 التسويات المالية
- **FR-130**: المحاسب ينشئ تسوية لتاجر تجمع كل الشحنات المستحقة التسوية ضمن فترة أو دفعة محددة.
- **FR-131**: اعتماد التسوية (Workflow: Draft → Pending Approval → Approved → Paid).
- **FR-132**: رفع مرفقات إثبات التحويل (صورة/PDF/إيصال) مرتبطة بالتسوية.
- **FR-133**: التاجر يرى كل تسوياته (رقم، قيمة، تاريخ، حالة، المرفقات) في بورتاله.

### 2.2.15 إدارة الوكلاء
- **FR-140**: بورتال وكيل مستقل: استقبال شحنات، توزيعها على مندوبي الوكيل الداخليين، متابعة التحصيلات والمرتجعات والعهدة النقدية بحوزته.
- **FR-141**: حساب مستحقات الوكيل (عمولة لكل شحنة مُسلَّمة بنجاح حسب اتفاقية الوكيل) وتسوياته بشكل مستقل عن تسويات التجار.

### 2.2.16 الشكاوى (Ticketing)
- **FR-150**: إنشاء تذكرة شكوى مرتبطة (اختياريًا) برقم شحنة، بأنواع محددة مسبقًا (شحنة مفقودة، تأخير، خطأ تحصيل، شكوى مندوب، شكوى وكيل، أخرى).
- **FR-151**: Workflow حالة التذكرة (Open → In Progress → Escalated → Resolved → Closed) مع SLA زمني لكل نوع.
- **FR-152**: سجل محادثة كامل داخل التذكرة (تعليقات + مرفقات) بين خدمة العملاء والتاجر.

### 2.2.17 مركز النشاط (Activity Center) و Audit Log
- **FR-160**: بث لحظي (Feed) لكل الأحداث المهمة (إنشاء/تعديل/حذف شحنة، تسوية، تعديل أسعار، تعديل صلاحيات) — عبر Polling دوري خفيف (كل 15-30 ثانية) متوافق مع cPanel (بديل عملي لـ WebSockets التي قد لا تتوفر على Shared Hosting؛ تُفعَّل WebSockets/Pusher لاحقًا عند الانتقال لـ VPS).
- **FR-161**: سجل تدقيق (Audit Log) شامل لكل عملية حساسة: المستخدم، التاريخ، الوقت، IP، GPS (إن وجد)، القيمة القديمة، القيمة الجديدة — قابل للبحث والتصفية والتصدير.

### 2.2.18 الإشعارات
- **FR-170**: محرك إشعارات موحّد (Notification Engine) يدعم قنوات متعددة لكل حدث، بأولوية وقناة احتياطية عند الفشل (مثال: WhatsApp أولًا، SMS احتياطي).
- **FR-171**: مصفوفة "الحدث ← القناة ← المستقبل" قابلة للتخصيص من لوحة الإدارة دون كود (تفصيل في [05-Workflows.md](./05-Workflows.md)).

### 2.2.19 التكاملات الخارجية
- **FR-180**: API عام موثّق (تفصيل كامل في [06-API-Design.md](./06-API-Design.md)) لإنشاء شحنات، الاستعلام عن الحالة، Webhooks لتحديثات الحالة.
- **FR-181**: Plugins/Connectors جاهزة لـ WooCommerce وShopify (عبر API عام)، وOpenCart وMagento (عبر نفس API العام بموصلات مخصصة لاحقًا حسب الأولوية الفعلية للعملاء).

### 2.2.20 التقارير و Dashboard الإدارة
- **FR-190**: مجموعة تقارير قياسية (تفصيل كامل في قسم 2.4 أدناه) قابلة للتصفية والتصدير (Excel/PDF) وجدولة الإرسال الدوري بالبريد.
- **FR-191**: Dashboard تنفيذي بمؤشرات KPI، رسوم بيانية، وخريطة مصر التفاعلية (بالمحافظات) لعرض توزيع الشحنات/الأداء جغرافيًا.

## 2.3 المتطلبات غير الوظيفية (Non-Functional Requirements)

| المعرّف | المتطلب | التفصيل |
|---|---|---|
| NFR-001 | الأداء | زمن استجابة الصفحات < 2 ثانية لـ 95% من الطلبات تحت حمل عادي |
| NFR-002 | التوفر | Uptime ≥ 99.5% شهريًا |
| NFR-003 | قابلية التوسع | البنية تدعم الانتقال من Shared Hosting إلى VPS/Cloud بدون إعادة كتابة الكود (فقط تغيير متغيرات بيئة + تفعيل Redis/Horizon) |
| NFR-004 | الأمان | تشفير كلمات المرور (bcrypt/argon2)، HTTPS إجباري، حماية CSRF/XSS/SQLi (مدمجة في Laravel)، Rate Limiting على كل API عام |
| NFR-005 | النسخ الاحتياطي | نسخ احتياطي يومي كامل لقاعدة البيانات + أسبوعي للملفات، بالاحتفاظ لـ 30 يومًا كحد أدنى |
| NFR-006 | التعدد اللغوي | عربي (أساسي، RTL كامل) + إنجليزي (اختياري) عبر Laravel Localization |
| NFR-007 | التوافق | يعمل على المتصفحات الحديثة + متوافق تمامًا مع الجوال (Responsive/Mobile-First خاصة لواجهة المندوب) |
| NFR-008 | قابلية الصيانة | التزام بمعايير PSR-12، تغطية اختبارات (Feature/Unit) للمسارات الحرجة (المالية والعهدة) لا تقل عن 70% |
| NFR-009 | إمكانية التتبع | كل عملية مالية أو تغيير حالة شحنة يجب أن تكون قابلة للتتبع الكامل (من فعلها، متى، من أين) |
| NFR-010 | الخصوصية | الالتزام بقانون حماية البيانات الشخصية المصري رقم 151 لسنة 2020 |

## 2.4 قائمة التقارير المطلوبة (تفصيل)

| التقرير | أهم الحقول |
|---|---|
| تقرير الشحنات | حسب الحالة/التاجر/الفرع/المحافظة/الفترة الزمنية |
| تقرير التحصيلات | المحصَّل مقابل المستهدف، حسب مندوب/فرع/وكيل |
| تقرير المرتجعات | نسبة الارتجاع حسب تاجر/منطقة/سبب |
| تقرير المندوبين | إنتاجية، نسبة نجاح، متوسط وقت التسليم |
| تقرير الوكلاء | شحنات موزعة، مستحقات، عمولات |
| تقرير الفروع | حجم الشحنات، الأداء، مخزون لحظي |
| تقرير التجار | حجم الأعمال، القيمة، نسبة النجاح، التصنيف |
| تقرير الأرباح | إيرادات الشحن − تكاليف التشغيل (وكلاء/مندوبين) لكل فترة |
| تقرير الأداء العام | SLA compliance، متوسط زمن دورة الشحنة الكاملة |
| تقرير Cash In Hand | العهدة النقدية الحالية لكل مندوب/وكيل/فرع مع تاريخ آخر توريد |

## 2.5 المزايا المتقدمة — تعريف تقني أولي (تفصيل التنفيذ في Future Scope)

| الميزة | آلية التنفيذ المقترحة |
|---|---|
| OCR لقراءة بيانات الشحنات | استخراج بيانات العنوان/الاسم من صور إيصالات/عناوين مكتوبة يدويًا عبر Tesseract OCR أو Google Vision API؛ استخدام أساسي: تسريع إدخال بيانات المرتجعات الورقية |
| AI Analytics | طبقة تحليلية فوق Data Warehouse (جداول تلخيصية Aggregated) + نماذج تنبؤية بسيطة (متوسطات متحركة، Regression) قبل التوجه لنماذج معقدة |
| Fraud Detection | قواعد Rule-based أولًا (نمط تحصيل غير طبيعي، تكرار "لا يرد" لنفس المندوب، فروقات متكررة في العهدة) قبل أي نموذج ML |
| Smart Routing / Auto Assignment | خوارزمية توزيع تلقائي للشحنات على المندوبين حسب: المنطقة الجغرافية، الحمل الحالي، الأولوية — Rule Engine قابل للتهيئة |
| Delivery Performance Prediction | نموذج تصنيف بسيط (احتمالية نجاح التسليم من أول محاولة) بناءً على بيانات تاريخية (منطقة، وقت، تاجر) |
| Automated Settlement Suggestions | اقتراح تلقائي لدُفعات تسوية جاهزة للتجار بناءً على قواعد (كل الشحنات المُحصَّلة والمستلمة بالشركة منذ آخر تسوية) |
| SLA Monitoring | مؤقتات (Timers) على كل حالة شحنة/تذكرة مع تنبيهات عند تجاوز الحد الزمني المتفق عليه |
| Live Driver Tracking | تحديث موقع GPS دوري من تطبيق/PWA المندوب (كل 30-60 ثانية أثناء التفعيل) معروض على خريطة Leaflet |
| Heat Maps | تجميع بيانات جغرافية (نجاح/فشل/كثافة شحنات) وعرضها كطبقة حرارية فوق خريطة مصر |
