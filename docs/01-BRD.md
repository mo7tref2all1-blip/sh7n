# 1. وثيقة متطلبات الأعمال (BRD)

## 1.1 نظرة عامة على المشروع

شركات الشحن ونقل الطرود في مصر (Last-Mile Delivery) تعمل وفق نموذج تشغيلي متكرر:
تاجر إلكتروني يُنشئ شحنة ← الشحنة تُستلم من فرع أو مندوب ← تنتقل بين الفروع حتى تصل لمحافظة العميل ← تُسلَّم عبر مندوب داخلي أو وكيل خارجي في المحافظات البعيدة ← يتم تحصيل المبلغ (COD) أو تأكيد الدفع المسبق ← تتم تسوية المستحقات مع التاجر دوريًا.

هذا النموذج يتطلب تتبعًا دقيقًا لأربعة مسارات متوازية في كل لحظة:
1. **مسار الشحنة الفعلي (Physical Movement):** أين الطرد الآن؟
2. **مسار الحالة التشغيلية (Operational Status):** هل تم التسليم أم لا؟
3. **مسار الحالة المالية (Financial Status):** هل المبلغ تم تحصيله، وهل وصل للشركة، وهل تمت تسويته للتاجر؟
4. **مسار العهدة (Custody):** من المسؤول قانونيًا/تشغيليًا عن الطرد أو النقدية الآن؟

معظم الأخطاء والنزاعات في شركات الشحن المصرية تنشأ من الخلط بين هذه المسارات الأربعة (مثال: اعتبار الشحنة "تم تسليمها" يعني تلقائيًا أن "المبلغ وصل للشركة" — وهذا غير صحيح، فالمبلغ قد يكون لا يزال في عهدة المندوب).

## 1.2 أصحاب المصلحة (Stakeholders)

| الجهة | الاهتمام الأساسي |
|---|---|
| مالك شركة الشحن (Company Owner) | الرؤية المالية الكاملة، الأرباح، أداء الفروع والوكلاء |
| مدير العمليات | تدفق الشحنات، حل الاستثناءات، الأداء التشغيلي اليومي |
| مدير الفرع | مخزون الفرع، عُهدة المندوبين، أداء الفرع |
| المحاسب | التسويات، الرصيد النقدي، مطابقة التحصيلات |
| خدمة العملاء | حل الشكاوى، التواصل مع التاجر والعميل النهائي |
| التاجر (العميل الأساسي للمنصة) | رؤية شحناته، تحصيلاته، تسوياته، تقاريره |
| المندوب | شحنات اليوم، التحصيل، العهدة النقدية بحوزته |
| الوكيل (شركة/فرد خارجي في محافظة بعيدة) | شحنات موزّعة عليه، عمولاته، تسوياته |
| العميل النهائي (Consignee) | تتبع شحنته، تأكيد الاستلام |

## 1.3 أهداف العمل (Business Goals)

1. توحيد إدارة دورة حياة الشحنة من الإنشاء وحتى التسوية النهائية في نظام واحد بدلاً من إكسل/واتساب.
2. تقليل نسبة الفاقد المالي الناتج عن سوء تتبع العُهد النقدية والشحنات.
3. تمكين التاجر من الاستقلالية الكاملة (Self-Service) في إنشاء الشحنات ومتابعتها دون تدخل بشري من الشركة.
4. تقليل زمن دورة التسوية المالية مع التجار من (أسبوعي/شهري يدوي) إلى تسويات دورية شبه آلية موثقة.
5. رفع الشفافية عبر تتبع لحظي لحالة كل شحنة وموقعها وعهدتها.
6. بناء بنية قابلة للتوسع لدعم نمو الشركة من عشرات الشحنات يوميًا إلى عشرات الآلاف دون إعادة بناء النظام.
7. خفض تكلفة التشغيل عبر أتمتة التسعير، التخصيص، والإشعارات.

## 1.4 نطاق العمل (Scope)

### داخل النطاق (In Scope) — النسخة الكاملة المستهدفة
- إدارة المستخدمين والصلاحيات (RBAC).
- إدارة الفروع والمخزون الداخلي للشحنات.
- بوابة تجار متكاملة (Dashboard + API + رفع Excel).
- محرك دورة حياة شحنات قابل للتخصيص (Workflow Engine).
- نظام عُهدة (Custody Chain) لكل شحنة ولكل نقدية.
- QR/Barcode لكل شحنة.
- تطبيق/واجهة مندوب (PWA أولاً).
- نظام إثبات تسليم (POD) مرن وقابل للتخصيص لكل تاجر.
- طرق دفع متعددة وفصل الحالة المالية عن حالة الشحنة.
- وحدة العهدة النقدية (Cash In Hand).
- محفظة إلكترونية للتجار وللوكلاء (Wallet + Ledger).
- محرك تسعير مرن (محافظة/منطقة/وزن/خدمة + تسعير مخصص لكل تاجر + باقات).
- تسويات مالية موثقة (اعتماد، مرفقات، سجل).
- بوابة وكلاء مستقلة.
- نظام شكاوى (Ticketing).
- Activity Center + Audit Log.
- إشعارات متعددة القنوات (WhatsApp / SMS / Email / Push / In-App).
- تكاملات خارجية (WooCommerce / Shopify / OpenCart / Magento) عبر API.
- تقارير شاملة + Dashboard تنفيذي بخرائط ومؤشرات.
- مزايا متقدمة اختيارية (OCR، AI Analytics، كشف الاحتيال، التوجيه الذكي...) — ضمن النطاق المستقبلي (انظر Future Scope).

### خارج النطاق (Out of Scope) في المرحلة الأولى
- تطبيق موبايل Native (Flutter) — يُؤجَّل لِما بعد التحقق من نجاح MVP.
- الشحن الدولي / الجمارك.
- تعدد شركات الشحن على نفس المنصة (Multi-Tenant SaaS لعدة شركات شحن مستقلة) — النظام مصمم لخدمة شركة شحن واحدة بفروعها ووكلائها؛ يمكن توسيعه مستقبلًا لـ Multi-Tenant حقيقي (انظر Future Scope).

## 1.5 السوق المصري — اعتبارات خاصة يجب مراعاتها في التصميم

1. **الدفع عند الاستلام (COD) هو الغالب** — أكثر من 80% من عمليات الشحن في مصر تعتمد على COD، لذلك نظام التحصيل والعهدة النقدية هو **قلب المنصة** وليس ميزة ثانوية.
2. **التقسيم الجغرافي المصري:** محافظة → مركز/قسم → منطقة/حي → قرية (للريف). يجب أن يدعم محرك التسعير والمناطق هذا التسلسل الهرمي بدقة (القاهرة الكبرى تختلف تسعيرًا عن الصعيد والحدود).
3. **الوكلاء الخارجيون (Franchise Agents):** في المحافظات البعيدة (أسوان، الوادي الجديد، مرسى مطروح، شمال/جنوب سيناء) تعتمد أغلب شركات الشحن على وكلاء محليين بدلاً من فروع مباشرة — يجب أن يكون نموذج الوكيل مستقلًا ماليًا وتشغيليًا عن نموذج الفرع.
4. **رقم الهاتف كمعرّف أساسي:** غالبية التواصل مع العميل النهائي والمندوبين عبر واتساب/مكالمات، وليس البريد الإلكتروني — لذلك WhatsApp Cloud API له أولوية أعلى من Email.
5. **"لا يرد" (No Answer) كحالة شحنة شائعة جدًا:** يجب أن يدعم النظام محاولات تسليم متعددة (Delivery Attempts) مع سجل زمني لكل محاولة.
6. **رفض استلام السعر:** شائع عند اختلاف السعر المعروض للعميل عن المتوقع — يجب أن يدعم النظام "تعديل السعر عند التسليم" مع موافقة العميل وتسجيل الفرق.
7. **قانون حماية البيانات المصري (Law No. 151/2020):** يجب مراعاة أساسيات حماية البيانات الشخصية (بيانات العملاء، أرقام الهواتف، العناوين) — تشفير، صلاحيات وصول محكومة، سجل تدقيق.
8. **الفوترة الإلكترونية / الضريبية:** يُفضَّل تصميم وحدة التسويات بحيث تدعم لاحقًا الربط مع منظومة الفاتورة الإلكترونية المصرية (ETA) إن احتاجت الشركة ذلك مستقبلًا.

## 1.6 مؤشرات نجاح المشروع (Success KPIs)

| المؤشر | الهدف |
|---|---|
| نسبة التسليم الناجح من أول محاولة (First Attempt Success Rate) | ↑ عبر تتبع دقيق للعنوان والتواصل المسبق |
| متوسط زمن دورة التسوية مع التاجر | من دورة يدوية غير منتظمة إلى دورة ثابتة (أسبوعية/كل 3 أيام) موثقة بالكامل |
| نسبة الفروق/الفاقد في العهدة النقدية | تقارب الصفر عبر المطابقة اليومية الآلية |
| زمن استجابة الشكاوى | مؤشر SLA قابل للقياس داخل النظام |
| نسبة اعتماد التجار على الرفع الجماعي (Bulk Excel/API) بدل الإدخال اليدوي | ↑ كمؤشر نضج تشغيلي |
| Uptime المنصة | ≥ 99.5% (واقعي لبيئة cPanel مُدارة جيدًا) |

## 1.7 المخاطر والافتراضات

**افتراضات:**
- الاستضافة الأولية cPanel (مشتركة أو VPS بلوحة cPanel) تدعم PHP 8.3+، MySQL 8، Cron Jobs، SSH (يُفضَّل للنشر عبر Git/Composer).
- عدد الشحنات المتوقع في أول 6 أشهر لا يتجاوز نطاق يمكن لخادم cPanel متوسط التعامل معه (حتى ~5,000-10,000 شحنة/يوم)؛ أي نمو أكبر يستدعي الانتقال لـ VPS مخصص/Cloud (مغطى في خطة التوسع).

**مخاطر رئيسية:**
| الخطر | التأثير | خطة التخفيف |
|---|---|---|
| قيود موارد استضافة cPanel المشتركة (لا Redis، لا معالجة خلفية حقيقية) | تأخر المهام غير المتزامنة (إشعارات، تقارير ضخمة) | استخدام Database Queue Driver + Cron كل دقيقة، وتصميم الكود بحيث يسهل التحويل لـ Redis/Supervisor عند الترقية لـ VPS |
| رفع ملفات Excel ضخمة (آلاف الشحنات) يستهلك الذاكرة | Timeout / فشل الرفع | معالجة الرفع عبر Queue Job مجزأ (Chunked Import) وليس تنفيذًا مباشرًا |
| اعتماد كامل على مزود WhatsApp Cloud API | توقف الإشعارات عند تعطل الخدمة | قناة بديلة SMS تلقائية عند فشل واتساب |
| تعقيد نموذج الحالة المالية/التشغيلية للمستخدمين الجدد | أخطاء تشغيلية بشرية | تدريب + واجهة تُظهر الحالتين معًا بوضوح مع ألوان/شارات مميزة |
